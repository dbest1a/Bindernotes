# Database runtime checks and reconciliation

Historical SQL files remain unchanged. `migration-bundle.mjs` combines the two reviewed 0016 files into one version **only in a new staging directory**, recording the normalized SHA-256 of each source. Unknown duplicate versions fail. Do not push directly from the historical source directory.

Before an existing database upgrade, run `inspect-migration-history.sql` read-only against the explicitly selected environment and retain the results privately. A recorded 0016 does not identify which file ran. Object presence alone does not prove equivalent policies or statements. Supported paths are a clean database, the complete historical chain through 0015, and the complete recovery schema through 0025 with both 0016 components. Partial schemas, ambiguous 0016 or unexpected history require a reviewed environment-specific forward repair; automatic history rewriting is not provided.

## Database API

- `save_personal_content(p_kind,p_record,p_expected_revision,p_operation_id)` accepts `note`, `document` or `learner-note` and snake-case table fields. Exclude timestamps/revision from p_record. New/legacy revision is zero. The result is the saved row with incremented revision.
- `save_whiteboard_snapshot(p_board,p_expected_revision,p_create_version,p_operation_id)` accepts canonical scene_json/module_elements. Current scene and requested version commit together. The server determines ownership, payload measurements, version numbers and quota. Free/Plus retain three active boards; active Studio/Everything receive 20. Downgrades preserve existing boards and prevent new allocations above the limit.
- Stale revisions raise SQLSTATE 40001, CONTENT_REVISION_CONFLICT. Clients must preserve drafts and offer recovery choices. A stable operation UUID retries the identical request without a second version. Reusing an ID for another payload is rejected; replay after subsequent editing reports a conflict.
- Safe pin/archive/move metadata writes remain column-granted and increment revision. Direct content/title updates cannot bypass CAS. Direct creation cannot set revision. Private foreign parents are checked on direct writes too.
- `apply_catalog_seed(p_payload)` is service-role-only and writes allowlisted system/math catalog tables in one transaction. Browser operators cannot invoke it. No hosted seed was run during remediation.
- account_entitlements is owner-readable and service-write-only. Paid creator access never changes profiles.role. Creators manage only their own non-system binders/lessons and cannot manage roles, purchases, global templates or seeding.

The client and migration0027 require a coordinated deployment: old direct-content clients are denied rather than bypassing CAS. Rollback only to an RPC-compatible client; keep additive schema/data. Removing CAS protection is not a safe rollback. History reconciliation for production remains blocked until its actual recorded state and schema are reviewed.

Mutation receipts contain hashes, identity and revision, not document payloads. Define an offline-retry retention horizon before a future service maintenance job prunes receipts; this migration never deletes student data or old versions.

## Trash and whiteboard retention

Migration0031 gives personal folders/courses/documents/notes one trash model: parent archive hides the tree without rewriting child archive flags or relationships. Items remain indefinitely until their owner explicitly confirms permanent deletion from trash. Restore the parent first; independently trashed children stay trashed. Direct authenticated DELETE is revoked. `set_personal_trash(kind,id,action,confirmation)` authorizes each owner and requires the literal `DELETE` for permanent subtree deletion. The UI disables destructive actions while the current editor has unsaved changes. Account-wide disposal is a separate trusted operation.

Migration0032 stores scenes only in `scene_json` and modules only in `module_elements`. Before dropping compatibility copies, it verifies that every current and historical pair is equal; a mismatch fails and rolls the migration back for manual reconciliation. The runtime upgrade test proves this failure path and preservation of meaningful equal current/manual version payloads.

Whiteboards retain the newest **50 automatic/draft versions** plus all explicit manual/checkpoint/snapshot versions. Pruning occurs transactionally on snapshot insertion; the current scene is never pruned. This bounds automatic growth while respecting explicitly retained checkpoints. Version history in the UI lists the latest100 retained versions. `restore_whiteboard_version(board_id,version_id,expected_revision,operation_id)` validates ownership, uses CAS, creates a new snapshot and promotes the chosen recovery point to a retained manual checkpoint. Recovering never mutates the old version's payload. Tests cover56 generated snapshots, pruning, current/retained preservation, retry, stale conflict and cross-owner denial. Coordinated deployment is required because old clients selecting the removed alias columns will fail.

## Native Auth and PostgREST browser environment

`start-local-api-stack.mjs` creates a separate random database in the loopback PostgreSQL runtime, runs **real GoTrue auth migrations**, applies the application migration bundle, and starts real GoTrue and PostgREST behind a tiny route-only HTTP proxy. It creates four disposable Auth accounts and seeds the actual catalog transactionally. It never loads `.env` or contacts the hosted database. Existing occupied API ports cause it to refuse startup.

Set `BINDERNOTES_LOCAL_RUNTIME` to the outside-repository native runtime directory containing `pgsql/bin/psql.exe`, `pgmq-1.5.1.sql`, `gotrue.exe` and `postgrest/postgrest.exe`. PostgreSQL must already listen on `127.0.0.1:55439`. No system install is required. Runtime logs and `local-api-stack.json` (local passwords and anon key) stay outside Git. Read that manifest programmatically to configure Vite; do not print it into reports or commit it.

```sh
node scripts/database/start-local-api-stack.mjs
node scripts/database/check-local-api-stack.mjs
```

The gateway is `http://127.0.0.1:55442`; Auth listens on 55440 and PostgREST on 55441, all loopback-only. The proxy only routes requests and adds localhost CORS headers. It does not fabricate authentication or database results. The HTTP smoke verifies four actual password sign-ins, refresh-token exchange, owner-only profiles, denied role escalation, note snapshot persistence/readback, idempotent retry, denied cross-owner access and stale-revision rejection. Its temporary note is deleted afterward. Services remain running for browser journeys; the manifest records their PIDs and the exact disposable database name for deliberate teardown after verification.

## Private files (BE22)

Migration0033 reserves immutable owner/UUID paths in the private `private-assets` bucket. Supported types are PDF, PNG, JPEG and WebP, at most50MiB per file and500MiB reserved per account. Owner-advisory locking proves concurrent reservations cannot exceed that allowance. Browser roles may insert only a reserved pending path; overwrite and direct deletion are denied. Old tutorial object policies are migrated to the existing private admin helper, fixing their revoked public-helper dependency.

Client TUS1.0 uploads send6MiB chunks; durable journals contain the owner, asset UUID and upload URL, never tokens or file bytes. Resuming requires selecting the same original file. An uncertain PATCH is reconciled with HEAD. The trusted completion endpoint streams the object and verifies actual size, magic bytes and SHA256 before the service-only completion RPC makes it ready. These checks detect mismatched files; they are not malware scanning or PDF text extraction. Signed read URLs last60seconds. Imported files stay `staged` under an owner/import-batch UUID until the archive transaction promotes them; failed imports are not shown as completed files.

Deletion first marks a retryable `deleting` row, then removes bytes through Storage, then deletes metadata only after the object row is absent. A restricted cleanup endpoint retries pending/staged/deleting rows older24hours. **Configure an actual scheduled caller before activation; this repository does not claim a job has run.** Server variables are `ASSET_UPLOADS_ENABLED=true`, `APP_ORIGIN`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ASSET_CLEANUP_SECRET`. Client activation requires `VITE_PRIVATE_ASSETS_ENABLED=true`; it remains off by default until real nonproduction Storage HTTP upload/download/delete, timeout/expiry and cleanup scheduling pass. Never put service/cleanup secrets in VITE variables.

Native tests execute real Storage table RLS, cross-owner denial, reserved-path writes, service-only completion, hidden import staging, delete fencing and12concurrent quota reservations. TUS and trusted streaming handlers have protocol/contract tests. **Physical Storage HTTP, signed URL expiry enforcement, TUS server behavior and delivered binary deletion remain unverified locally.** The native gateway deliberately returns501 for Storage; no fake upload success is substituted. Official Storage's filesystem backend requires POSIX extended attributes and was not ported to Windows.

## Account lifecycle (BE21)

Migration0035 checks authenticated API access against the real GoTrue `auth.sessions` row and owner profile. A revoked session is denied immediately by restrictive RLS on application/Storage tables and guards on direct writes and authenticated mutation RPCs, including their receipt-replay paths. It does not rely on JWT expiry. Future application tables/RPCs must carry the same boundary. Native SQL fixtures seed explicit session rows; no weaker missing-session bypass exists. [Supabase session documentation](https://supabase.com/docs/guides/auth/sessions) explains why ordinary JWT signature checks alone cannot provide immediate revocation.

Recovery requests use Supabase Auth with a fixed same-origin `/auth/recovery` redirect, which must be added to the deployment's Auth redirect allowlist. Password updates require at least12characters in the UI and globally sign out afterward. The account page can retry pending deletion using its real Auth session even when the profile's data access is already denied. Global signout uses the existing save-before-signout boundary.

Trusted deletion requires same-origin POST, an Auth-validated session with authentication within5minutes, explicit DELETE confirmation and a stable operation UUID. Operator accounts are refused until shared content is deliberately transferred. The server checks actual Stripe subscription and open-checkout state under the existing billing lease; nonterminal subscriptions, open checkout, incomplete provider pages or network errors prevent deletion. A shared owner lock and durable deletion marker fence both content writes and new billing/customer operations. The marker is set before enumerating files. Storage removal must succeed before Auth admin deletion cascades owned relational data. Failures keep a retryable marker and the account; no false completed response is returned. Owner-keyed browser journals are cleared after confirmed deletion; unidentifiable legacy device-only entries require clearing site data manually.

Configure server-only `ACCOUNT_DELETION_ENABLED=true`, `APP_ORIGIN`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and Stripe configuration when billing customers exist. Client deletion is off unless `VITE_ACCOUNT_DELETION_ENABLED=true`. Do not enable before real Storage/billing gate verification. Native test-only `check-local-account-lifecycle.ts` refuses remote hosts, creates a fresh disposable user, consumes a real generated recovery token, proves password replacement/global session invalidation and executes the trusted handler against real GoTrue/PostgREST. It preserves the browser test users. Generating the recovery token through the admin API verifies recovery semantics, **not email delivery**. Hosted email allowlists, OAuth reauthentication, actual Storage removal and Stripe test-mode end-to-end deletion remain release gates.

## Generated schema types (BE34)

`generate-types.mjs` introspects the actual disposable PostgreSQL catalog, never application row data. It generates68 public tables and63 RPC names through0040, including ordered columns/defaults/nullability, enum values, foreign-key relationships and unique-key cardinality. Function inputs admit SQLNULL because PostgreSQL arguments have no NOT NULL declaration; runtime domain validation and RPC guards still enforce required values. Table nullability remains exact. `--check` fails if the generated artifact differs. The disposable runtime suite runs that comparison against both clean and upgrade databases before teardown, so stale hand-maintained types are not silently accepted. To regenerate from the existing local Auth stack, set `BINDERNOTES_LOCAL_RUNTIME` and run `node scripts/database/generate-types.mjs`. The main browser Supabase client is typed; unknown editor/canvas payloads pass runtime JSON validation at write boundaries. JSONB domain schemas remain necessary because SQL only knows the JSON container type.

The typed client exposed missing History source quote/support/challenge columns;0036 adds them without discarding source text or weakening ownership. Their real role roundtrip is included in the database suite.

Tutorial upload compensation now journals planned new paths before uploading. If a poster or metadata write fails, cleanup first queries whether a saved tutorial references each exact path; it never deletes a referenced object after a lost acknowledgement. Uncertain reference lookups/removals leave a durable owner-scoped journal, retried before the next tutorial upload. Existing published media is not silently pruned. This browser retry mechanism requires that browser's journal; cross-device/abandoned-browser tutorial cleanup is not claimed as a deployed scheduled job.

Migration0038 refuses creator deletion while owned published content or foreign-owned binder/lesson children still depend on the account. This avoids FK cascades erasing another learner's notes, highlights, comments or enrollments. The trusted HTTP preflight explains the required operator transfer, and the transaction rechecks the rule under the account deletion lock. A real SQL fixture verifies a foreign learner note survives the refused deletion and subsequent explicit source transfer.

Migration0039 exposes only the current JWT's own server-session status (`active`, `deleting`, or `revoked`). Route changes, returning to the foreground and denied data actions trigger a check. A confirmed revocation retires the UI identity and presents sign-in while retaining owner drafts; a network failure keeps the session and offers retry. Pending deletion preserves session-only access to Account. Late status responses cannot clear a newer account. There is no background polling or destructive SDK sign-out race.

Source-dependent child inserts and relationship changes share the source owner's deletion lock. The0038 guard either observes the committed foreign dependency and refuses deletion, or observes the deletion marker and refuses the attachment. A separate-connection concurrency fixture proves both operations cannot commit together.

Migration0040 closes the private quiz-set parent boundary: attempts require the same owner unless the quiz is an operator catalog entry with no owner. Parent ownership changes lock against new attempts. Legacy foreign-owned attempts are preserved and block account deletion until an operator deliberately resolves the shared source.
